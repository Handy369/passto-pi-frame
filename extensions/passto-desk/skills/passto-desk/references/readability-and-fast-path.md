# Readability and Fast Path

## Fast path

用户显式提到：
- `passto-desk`
- 共享白板 / 工作台
- “先搭个骨架”
- “先画个结构图”

则优先走 fast path：
1. create / bind room
2. 先整理 semantic objects / relations
3. 再整理一个最小 `view`
4. 生成 `passto-desk-domain-json/v3`
5. import_domain_json
6. 回读后再补充细节

## First-pass readability policy

首轮目标不是完整，而是**读得懂**。

默认首轮策略：
- 控制节点数量
- 先放主干路径
- decision 节点显式用 diamond
- state / action 视觉区分
- lane / group 只在确有助于理解时加入
- note / annotation 只承载必要补充，不抢主干
- legend 只在确有帮助时加入
- annotation 优先贴近被说明对象的阅读语境
- 关系短 label 优先
- 长注释不要塞进主干节点
- 不要生成大量交叉线
- 不要为了“信息全”牺牲可读性

## Explain-first self-review protocol

当当前任务的主要目标是“先给人看懂”，而不是“先保证工程回读完整”时，agent 在首轮图完成后**不要立刻提交**，而应先做一次 explain-first 自评。

默认流程：
1. 先完成首轮解释图 / 最小骨架图
2. 切换到“审稿者视角”而不是“作者视角”
3. 先按解释图维度逐项打分并写一句理由
4. 再按机制实现维度检查主干是否稳固
5. 若有低分项，先自我修图一轮
6. 再提交给用户，或再进入结构化增强

### A. 解释图评分维度

每项 1~10 分，并必须附一句理由：
- 主干清晰度
- 阅读入口
- 视觉层级
- 版式节奏
- 信息取舍

### B. 机制实现评分维度

每项 1~10 分，并必须附一句理由：
- 节点绑定完整度
- 边连接完整度
- relation label 归属清晰度
- 锚点稳定性
- 编辑稳健性

可选补充：
- Excalidraw 机制利用度（总评项）

### 自评时必须问自己的问题

#### 主干清晰度
- 用户能否在几秒内看出这张图主要在讲哪条主流程？
- 主干是否被次要分支、注释、长文本冲淡？
- 是否存在必须来回扫视才能理解的路径？

#### 阅读入口
- 图上是否清楚说明“这是什么图”？
- 是否有标题、摘要、开始点或明显起始入口？
- 第一次看图的人是否知道该从哪里开始读？

#### 视觉层级
- 最重要的节点是否在尺寸、位置、颜色、样式上更突出？
- 决策、处理、异常、说明是否有角色区分？
- 是否存在所有东西看起来一样重的问题？

#### 版式节奏
- 阅读路径是否顺滑，还是经常被迫大幅左右跳转？
- 节点之间是否过挤或过散？
- 分支与主干是否形成稳定节奏，而不是局部突兀鼓包？

#### 信息取舍
- 是否只保留了首轮理解真正需要的信息？
- 是否把实现细节、边角说明、次要关系塞得过多？
- 这张图是在帮助理解，还是在焦虑式求全？

#### 节点绑定完整度
- 主干节点的文字是否默认绑定到容器，而不是靠位置贴上去？
- 是否还有关键节点依赖“独立 text + 手工对齐”表达归属？

#### 边连接完整度
- 主干关系是否真正连接起止对象，而不是自由画线？
- 移动节点后，主干边是否应当稳定跟随？

#### relation label 归属清晰度
- “是 / 否 / retry / fail / spawn / fork” 等标签是否明确属于某条边？
- 它们是否仍然只是飘在线旁边的自由文字？

#### 锚点稳定性
- 主干边是否优先使用稳定的上/下/左/右连接策略？
- 是否存在随机接边、连接点漂移、方向混乱的问题？

#### 编辑稳健性
- 如果用户稍后移动节点、改文本、补分支，这张图是否容易散架？
- 当前实现是否更像“真正可编辑对象关系”，而不是一次性截图式摆放？

#### Excalidraw 机制利用度（可选总评）
- 当前图是否只是“看起来像机制正确”，还是确实利用了容器绑定、边连接、关系归属？
- 主干是否已经达到 mechanism-first，而不是纯坐标拼贴？

### 软阈值

#### 解释图阈值
- 主干清晰度 < 8：建议重做主干组织
- 阅读入口 < 8：必须补标题 / 摘要 / 开始入口
- 视觉层级 < 7：建议强化角色区分
- 版式节奏 < 7：建议重排布局
- 信息取舍 < 7：建议删减次要信息

#### 机制实现阈值
- 节点绑定完整度 < 7：主干节点应补容器绑定
- 边连接完整度 < 7：主干边应补对象连接
- relation label 归属清晰度 < 7：关键分支标签应显式归边
- 锚点稳定性 < 7：建议统一主干连线锚点策略
- 编辑稳健性 < 7：说明当前图仍偏一次性摆放，需回到机制实现层修正

如果加入总评项：
- Excalidraw 机制利用度 < 6：允许先作为解释图样板提交，但必须记录为后续机制优化项

### 推荐输出格式

```md
自评（解释图标准）
- 主干清晰度：8/10 —— 主线明确，但某些分支仍略抢戏
- 阅读入口：9/10 —— 标题、摘要、开始点都比较明确
- 视觉层级：7/10 —— 主次存在，但局部节点权重仍偏平均
- 版式节奏：6/10 —— 横向略长，阅读带不够稳定
- 信息取舍：7/10 —— 解释够用，但说明区略偏多

自评（机制实现标准）
- 节点绑定完整度：6/10 —— 部分主干节点仍是文字与框体分离
- 边连接完整度：6/10 —— 有些主干边已绑定，但仍有自由线段
- relation label 归属清晰度：5/10 —— 分支标签语义清楚，但实现上仍偏漂浮
- 锚点稳定性：6/10 —— 已有部分稳定连接，但整体策略尚不统一
- 编辑稳健性：5/10 —— 继续编辑时仍有散架风险
- Excalidraw 机制利用度：6/10 —— 已部分机制化，但未形成一致默认规则

是否需要自我修图：需要
优先修改项：
1. 收缩横向跨度
2. 降低次要分支权重
3. 把主干节点与主干边统一升级为绑定实现
```

### 可直接复用的提示词

> 你已经完成首轮解释图。现在不要立刻提交，先切换到审稿视角，分两组标准自评这张图。第一组按“解释图标准”评分：主干清晰度、阅读入口、视觉层级、版式节奏、信息取舍。第二组按“机制实现标准”评分：节点绑定完整度、边连接完整度、relation label 归属清晰度、锚点稳定性、编辑稳健性。每项给出 1~10 分和一句理由。可选补充：Excalidraw 机制利用度总评。然后判断这张图是否需要先自我修订一轮；如果需要，请列出最多 3 个最优先修改项。评分标准不是工程回读完整性，而是“这张图是否既讲得清，又作为 Excalidraw 对象关系画得稳”。

## Minimal skeleton rule

当信息很多时，首轮至少只保留：
- 关键对象
- 主干关系
- 关键分支
- 少量必要说明

其余内容：
- 放到下一轮再加
- 或拆成另一张视图

## Explicit relation rule

“不要靠位置表达关系”不是一句风格建议，而是运行规则：
- object relation 必须进入 `semantic.relations`
- 哪些 relation 被显示，必须进入 `view.visibleRelations`
- relation 如何转成视觉连线，必须进入 `mapping.relationToEdge`
- relation label 应结构化保存，而不是只放在图上附近

## Mapping rule

必须承认 agent 视图和人类视图是两套视图：
- agent 关心对象、关系、可编辑结构
- 人类关心阅读路径、视觉层级、版面

因此修改图时，不要只改 Excalidraw 元素；优先改 v3 的：
- `semantic`
- `view`
- `mapping`
- `visual`

当用户表达“这几块是一组”“这两个角色分开看”时：
- 优先用 `view.groups` / `view.lanes` 表达
- 不要只靠把节点围在一个框里或摆成上下两排来暗示结构

当用户表达“这条规则补充说明一下”“给我一个图例”时：
- 优先进入 `semantic.notes`
- 再通过 `view.members` / `mapping` 落到 note / legend 节点
- 不要默认放成无主 free text

当用户表达“给这一步加一句附注 / 限制条件 / 特殊说明”时：
- 优先用 `annotation`
- 视觉上与普通 note 区分
- 布局上尽量贴近被说明对象，但不要破坏主干
- annotation 已知 target 时，应优先按 target 做就近布局，而不是落回通用说明区
- 如果目标明确，应保留 `annotation.target` 绑定

## Mechanism-first realization for primary structure

Explain-first 不等于可以用“坐标拼贴”实现主干。

当当前图的主要目标是解释而不是穷尽时，允许在信息量、细节量、次要关系显隐上做取舍；但**主干节点、主干关系、关键分支标签**仍应优先按 Excalidraw 的对象机制来实现，而不是只追求“看起来像”。

### 核心原则

- 主干节点优先使用容器主体 + 绑定文本
- 主干边优先绑定起止对象，而不是自由箭头
- 关键分支标签应有明确 relation 归属，而不是游离 free text
- 主干连线优先采用稳定锚点策略，而不是随机接边
- 说明区、补充注释、装饰性元素可以比主干拥有更高的自由摆放容忍度

### 不允许的退化

以下情况即使在 Explain-first mode 下也不应成为默认：
- 用独立 text 靠位置贴在主干框体上，长期替代绑定文本
- 用自由箭头替代主干对象之间的连接
- 把 “是 / 否 / retry / fail / spawn / fork” 等关键分支标签做成完全游离的文字
- 主干节点一移动，边和标签就明显散架

### 允许的策略取舍

Explain-first mode 可以：
- 暂时隐藏次要 relation
- 暂时不展开所有 mapping 细节
- 把一些补充说明放入 note / annotation 区
- 为了首轮易读性减少结构暴露量

Explain-first mode 不可以：
- 牺牲主干对象关系的机制正确性
- 把主干退化成一次性截图式摆放

### 一句话要求

> 首轮可以先讲清，但主干必须先画稳。

## Fallbacks
- 优先保留语义，不要伪造关系
- 优先缩小当前视图范围
- 优先拆图
- 优先把复杂说明留到注释区 / 下一轮
- lane / group 如果当前回读不稳，也应保留结构声明而不是只留视觉框
- note / legend 如果暂时无法优雅布局，也应保留结构对象，不要退化成随意 free text
- annotation 如果无法安全贴近目标，也应保留结构属性并退到次级阅读区
- relation routing 应尽量避开 annotation 区、group 标题区、lane 标题区
- group / lane 若发生重叠或嵌套，优先保留显式结构标记而不是仅靠几何猜测

## Complexity valve

布局算法是需要的，但它应该有**阈值和阀门**，而不是无限吸收复杂度。

### 基本原则
- 小改动：优先局部处理，避免动整张图
- 复杂度升高：优先切换策略，而不是继续补兼容规则
- 结构改动主要由 agent 负责时，应优先回到 domain v3 再生成，而不是把白板局部状态当作唯一真相源

### 何时继续局部处理
以下情形更适合继续局部布局：
- 新增元素很少，且只影响单个节点/单条关系附近
- 新 annotation / note 不会进入主干阅读带
- relation label 避让仍能在轻量规则内完成
- lane / group 边界没有被显著改写

### 何时触发策略升级
出现以下信号时，不应继续执着于 append 兼容：
- 新增元素开始跨多个结构块传播影响
- 为避免碰撞需要连锁挪动多个 annotation / label / container
- 主干阅读路径被局部补丁破坏
- 局部修复规则的数量已经超过结构重建的收益
- 人类能一眼看出“这张图该重排了”，agent 也应允许切换到重建模式

### 升级顺序
推荐按以下顺序升级，而不是一上来就做最复杂兼容：
1. 局部布局修正
2. 局部结构块重建
3. 基于 domain v3 的整图重生成

重点不是“永远不重建”，而是：
**在重建成本低于局部兼容成本时，应该主动重建。**

## Layout Algorithm (domain-json-to-excalidraw.mjs)

从 v3 domain JSON 到 Excalidraw scene 的布局转换由 `layoutFlowNodes` / `routeEdge` / `normalizeBBox` 串联完成。

### 全局列对齐（v2→v3 关键改进）

v2 布局中每个泳道的节点独立编号，导致跨泳道箭头产生大量反向（dx<0）路径：
- 同 **lane** 内：`x = startX + lanePosition * spacing`（lanePosition 只在该泳道内排序）
- 跨泳道箭头如 tool(泳道内第5位)→runtime(另一泳道第0位)，dx 为负，箭头向左甩

v3 改用**全局优先级排序**决定 X 位置：
```
globalSorted = [...members].sort((a,b) => a.priority - b.priority)
x = startX + globalPosition * primarySpacingX
```
所有泳道共享同一列网格。优先级 N 和 N+1 的节点始终在同一列，跨泳道箭头必然向右（dx>0）。

### 动态泳道 Y 位置

v2 自动 `laneGap=180`，与最大节点高度重叠导致泳道间垂直间隙为 0px。
v3 先计算每泳道最大节点高度，然后动态累加：
```
laneStartY[laneId] = currentY;
currentY += laneMaxHeights[laneId] + laneGap; // laneGap=80
```
保证泳道间始终有清晰间距。

### 参数默认值

| 参数 | v2 | v3 |
|---|---|---|
| primarySpacingX | 240（节点间仅28px间隙） | 280（68px间隙） |
| laneGap | 180（与节点高度重叠->0px） | 80（泳道间距+80px） |

这两个默认值可通过 `visual.layoutPolicy.primarySpacingX` 和 `visual.layoutPolicy.laneGap` 在 domain JSON 中覆盖。

### Bounding Box 标准化

新增 `normalizeBBox(startX, startY, points)`：计算所有点的 min/max，保证返回的 width/height 始终为正。
所有 `routeEdge` 返回值都经过 `normalizeBBox`，消除负宽度箭头导致 Excalidraw 不渲染的 bug。

### 箭头路由策略

- **dx>0（正向）**：肘点步长初始上限 120px，障碍规避可推至 dx×0.6
- **dx≤0（反向→v3 几乎消除）**：垂直优先 `[[0,0],[0,dy],[dx,dy]]`，不再向左甩
- **TB 方向**：同类策略，dy>0 肘点上限 120px，dy≤0 水平优先

## Anti-patterns

以下是高频错误：
- 从文本直接拼 elements
- 把对象关系写进节点长段落里
- 把 free text 放在箭头旁边冒充关系 label
- 大量节点平铺，主干不清
- 连线随机、方向混乱
- 把所有内容放一张图导致难读难改
