# Code Simplification

## Why

这个 Skill 用于压缩“代码能跑，但复杂度已经妨碍理解、修改和审查”的不确定性。

如果没有它，agent 很容易：
- 把“能工作”当成“不需要收敛”
- 一边简化一边悄悄改行为
- 为了更少行数而牺牲可读性
- 把局部简化扩成大规模无关重写

---

## What

### 主目标
把已工作的实现收敛成**行为不变、复杂度下降、审查成本更低**的版本。

### 主输出物
- 明确的行为边界
- 复杂度来源判断
- 局部简化改动
- 行为未变的验证证据

### 不负责
- 不替代新功能实现
- 不替代性能主导的优化
- 不在尚未理解代码职责时先动手简化
- 不把“重写模块”伪装成简化

它通常作为：
- `/Users/handy/.claude/skills/project-implementation/SKILL.md`
的 build 或 review 路径专项实现器被补入。

---

## Structure

默认只需单一 `SKILL.md`。

它在父 Skill 中真正改变的是：
- 首动作：先确认行为边界与复杂度来源，而不是直接重构
- 证据形状：从“看起来更优雅”变成“更易懂且行为未变”

---

## Flow

1. 先确认当前主问题确实是复杂度，而不是 bug、性能或需求不清
2. 先明确行为边界：输入、输出、错误路径、副作用、现有测试
3. 先定位复杂度来源：
   - 深层嵌套
   - 长函数
   - 重复逻辑
   - 命名含混
   - 抽象失衡
4. 再做局部简化，只改当前复杂度来源最集中的地方
5. 每次简化后立即验证行为未变：测试、类型检查、最小运行验证
6. 当理解成本已明显下降且行为仍稳定时停止，不继续扩成无关重构

### 关键约束
- 先理解，再简化
- 行为不变比形式更重要
- 清晰优先于炫技或压行数
- 默认只收敛最近改动或当前问题附近的代码

### 何时不该使用
- 代码职责还没搞清楚
- 当前主问题是失败修复或性能瓶颈
- 模块即将被整体替换

---

## Surface

这是一个局部强化型 Skill：
- 入口窄
- 只在复杂度成为主问题时补入
- 输出稳定围绕 boundary / complexity source / simplification proof

在父 Skill `project-implementation` 中，通常位于：
- build 收尾阶段
- review follow-up 阶段

---

## Runtime Proof

先验证：补入本 Skill 后，首动作是否真的从“直接重构”变成“先确认行为边界”。

再验证：
- 复杂度来源是否被明确命名
- 简化是否集中在当前主要复杂度上
- 行为验证是否存在
- 是否没有把简化扩成无关大重写

可接受 proof：
- human review
- tests / typecheck / minimal runtime verification
- downstream quality（后续修改与 review 成本是否更低）
