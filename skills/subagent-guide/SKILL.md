  Subagent 工具使用与并行分发指南。主工作流是：先判断当前任务是否适合委派或并行，
  再选择 spawn / fork 模式，把工作拆成自包含子任务，并安全回收结果。

  使用此技能的场景：
  1. 当前任务可以拆成 2 个或以上互不依赖的子任务，适合并行分配给 subagent
  2. 需要把 review、实现、分析、验证等 bounded work 隔离给独立子 agent 处理
  3. 需要对多个文件、多个方案、多个实验结果做并发分析或交叉验证
  4. 用户明确要求“用 subagent”“并行处理”“拆分任务”“分配给子 agent”

  应优先触发的场景：
  1. 用户提到“并行”“并发”“拆成几个任务”“分别检查”“分配给 subagent / 子 agent”
  2. 当前任务天然存在多个可独立推进的 workstream，例如：实现 / review / 测试 / 文档 可分开做
  3. 需要隔离上下文、获取独立第二意见、或让某个 bounded 子任务在独立进程中完成

  不要在以下场景触发：
  - 任务非常小，当前 agent 直接完成比委派更快
  - 子任务强依赖同一份实时上下文，拆开后会导致高额协调成本
  - 工作必须严格串行、频繁共享中间状态，或本质上只有一个单点动作

# Subagent Usage Guide

> **last_verified: 2026-05**

这个 skill 不只是解释 `subagent` 工具怎么用，**更重要的是提醒 agent 何时应该主动考虑委派与并行**。

很多任务并不是用户显式说“用 subagent”才适合委派。只要满足以下任一条件，就应该先评估是否值得使用 subagent：
- 有 **2 个以上互不依赖** 的子任务
- 需要 **独立第二意见 / 隔离 review**
- 需要对 **多个文件 / 多个候选方案 / 多份结果** 做并发处理
- 当前任务规模较大，串行执行会明显拖慢反馈速度

---

## 1. 先判断：这轮是否该考虑 subagent？

开始复杂任务前，先问自己这 4 个问题：

### Q1: 是否存在 2 个以上可独立推进的子任务？
- **是** → 优先考虑 subagent，尤其是并行 `tasks: [...]`
- **否** → 继续看 Q2

### Q2: 是否需要把某一部分工作隔离成独立进程更安全？
例如：
- 独立 code review
- 独立 verifier / 结果分析
- 独立文档整理
- 独立实现某个明确切片

- **是** → 考虑单个 subagent
- **否** → 继续看 Q3

### Q3: 子任务能否被写成自包含任务？
- **能** → 适合 `mode: "spawn"`
- **不能，且强依赖父上下文** → 评估是否值得 `mode: "fork"`
- **完全不能拆** → 当前 agent 自己做

### Q4: 委派收益是否大于协调成本？
- **大于** → 委派
- **不大于** → 不委派，直接完成

---

## 2. 默认应主动触发的高价值场景

以下场景即使用户没有明确说“用 subagent”，也应优先评估是否委派：

### 2.1 多文件并发分析
例如：
- 同时审查 3 个模块
- 同时比较多个配置文件
- 同时汇总多个日志 / 结果文件

### 2.2 实现 / review / 验证 分离
例如：
- 一个 subagent 负责实现
- 一个 subagent 负责审查或找风险
- 父 agent 负责整合与决策

### 2.3 多方案并行探索
例如：
- 并行比较 A / B 两种修复路径
- 并行评估不同设计方案
- 并行分析多个可疑 root cause

### 2.4 大任务中的 bounded slice
例如：
- 让子 agent 只处理某个目录
- 让子 agent 只补一组测试
- 让子 agent 只整理某份文档或报告

### 2.5 独立第二意见
例如：
- 高风险改动前先让 reviewer 型子 agent 做 fresh-context 审核
- 对结论不确定时，用独立子 agent 做交叉验证

---

## 3. 默认不该使用的场景

### 3.1 单步小任务
例如：
- 改一个很小的文本块
- 回答一个直接问题
- 读取单个文件后马上给结论

### 3.2 强串行、强共享状态任务
例如：
- 每一步都依赖上一步最新编辑结果
- 多个子任务会频繁改同一文件同一片区域
- 需要持续共享未落盘的中间推理

### 3.3 上下文总结成本高于执行成本
如果为了委派，你需要写一大段上下文才能让子 agent 开始，而这段上下文本身已经接近完成工作量，通常不值得委派。

---

## 4. Mode Selection Strategy

### 优先使用 `mode: "spawn"`（默认）
适用于**自包含任务**，例如：
- “为 `auth.ts` 写单测”
- “总结这个文件的风险点”
- “比较两个实现方案并给结论”

**优点**：
- 更便宜
- 更快
- 更少上下文污染

**规则**：
默认假设子 agent **不知道父对话历史**。因此 `task` 字符串必须写全必要上下文。

### 仅在必要时使用 `mode: "fork"`
只在以下情况使用：
- 子任务高度依赖父对话历史
- 任务依赖父 agent 已读取但不便完整复述的大量上下文
- 复述成本明显高于 fork 带来的 token 成本

**警告**：
`fork` 成本高，不要因为懒得总结就默认使用。

---

## 5. Delegation Guards（运行时约束）

### 5.1 深度限制
- 系统通常有最大 delegation depth（常见是 3）
- 如果你自己已经是 subagent，要先确认是否还有继续委派预算
- **策略**：接近深度上限时，优先自己完成，而不是继续下钻

### 5.2 循环防护
- 不能委派给 ancestry stack 中已出现的 agent
- 如果只是想要“再来一个观点”，不要形成循环委派；直接自己完成分析，或换一个独立任务角度

---

## 6. Robust Task Definition

### 6.1 Context Injection
在 `spawn` 模式下，子 agent **没有历史上下文**，所以任务必须自包含。

- ❌ Bad: `task: "Fix the bug discussed above."`
- ✅ Good: `task: "Fix the TypeError in src/index.ts line 42. The variable 'user' is undefined because the API response structure changed. Add a null check and keep existing behavior unchanged."`

### 6.2 明确 Done 条件
必须明确告诉子 agent：什么算完成。

例如：
- `仅返回 review findings，不要改代码`
- `完成后给出修改文件列表 + 核心变更摘要`
- `输出严格 JSON`
- `只实现 tests/ 目录下的失败测试修复`

### 6.3 任务边界要收窄
好任务应该是：
- 边界清楚
- 输出明确
- 最好只负责一个结果物

避免：
- “顺便看看还能优化什么”
- “把整个系统都检查一下”
- “如果有空再做点别的”

---

## 7. Parallelism

### 如果任务相互独立，优先用并行 `tasks: [...]`
典型模式：
- 并行看多个文件
- 并行比较多个方案
- 并行回收多组实验结果
- 并行做实现 / review / 验证

### 不要并行化彼此依赖的任务
以下情况不要并行：
- Task B 依赖 Task A 的产出
- 多个子任务会改同一文件的相邻区域
- 父 agent 还没决定方案，子 agent 却先各自开工

### 推荐的并行拆分粒度
优先拆成：
- 按文件 / 目录
- 按角色（实现 / 审查 / 验证）
- 按方案（A / B / C）
- 按结果集（日志 1 / 日志 2 / 日志 3）

不要拆成：
- 高耦合、随时需要同步的小碎片

---

## 8. 可直接套用的委派模式

### 模式 A：并行分析
- 子 agent 1：分析模块 A
- 子 agent 2：分析模块 B
- 父 agent：整合结论

### 模式 B：实现 + 审查
- coder 子 agent：按明确 contract 实现
- reviewer 子 agent：检查风险与缺口
- 父 agent：决定是否采纳并落地

### 模式 C：多方案比较
- 子 agent 1：给出方案 A
- 子 agent 2：给出方案 B
- 父 agent：比较 tradeoff，选最终方案

### 模式 D：结果回收
- 多个子 agent 各自读取一组输出
- 父 agent 统一汇总成一份结论

---

## 9. Available Agents

始终查看系统提示里的 Available Subagents / runtime profiles：
- 如果没有专门专家可用，优先用 `default`
- 审查类任务优先 `reviewer`
- 明确实现类任务优先 `coder`

如果系统里没有列出某个特化 agent，不要假设它存在。

---

## 10. Positive / Negative examples

### Positive（应该主动考虑 subagent）
- “把这 4 个文件分别审一下，然后汇总风险”
- “并行比较两个修复方案哪个更稳”
- “一个 agent 写实现，另一个 agent 做 review”
- “把日志、测试失败、构建报错分别分析，再给我统一结论”

### Negative（不该为了用而用）
- “帮我改这一行文案”
- “看一下这个函数返回什么”
- “先读这个文件，再告诉我有没有 bug”
- “这个任务全程依赖刚刚产生的最新编辑结果，无法切分”
