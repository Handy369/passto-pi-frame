# UI/UX Product Design

> **last_verified: 2026-05-16**
> positioning: unified UI/UX definition router for product interfaces

## 作用

这是统一的 **UI/UX / UE / 交互设计** 主入口。

核心原则只有一个：
> **UI/UX 不能把“信息结构”与“视觉效果”拆成两个互相竞争的入口。应先解决对象、结构、层级、布局与决策路径，再用视觉手段做增强。**

也就是说，本模块默认按下面顺序工作：
1. **信息结构**：对象是什么、谁在使用、当前任务是什么、哪些信息最重要
2. **内容层级**：什么该先看、什么该常驻、什么该条件出现、什么该折叠
3. **功能布局**：主操作在哪、状态在哪、待处理项在哪、异常与恢复在哪
4. **反馈与去歧义**：用户如何确认系统当前状态、是否生效、下一步是什么
5. **视觉增强**：排版、颜色、对比、密度、留白、图标、动效

视觉不是不重要，而是**不应先于结构问题被讨论**。

---

## 本质：UI/UX / 视觉 / 交互设计是在传递信息

无论是信息结构、内容布局，还是颜色、字号、对比、动效，
本质上都在做同一件事：

> **以多种方式传递信息，分配有限注意力，并尽量消除信息歧义。**

好的界面不是“把所有需要展示的信息都展示出来”，
而是主动回答：
- 哪些信息最值得先被注意到
- 哪些信息只应作为辅助背景
- 哪些信息应该在特定时机才出现
- 哪些信息必须通过结构、位置、视觉权重被强化
- 哪些信息应该被折叠、延后、降噪或移出首屏

这和 prompt 设计里“开头和结尾更容易被 LLM 注意到”是同一类问题：
**注意力永远有限，因此设计的职责不是平铺信息，而是安排信息。**

---

## 什么是 UX 可用性设计

可用性不是单纯“好不好看”，而是衡量：

> **特定用户能否在特定场景中，以有效、低负担、令人满意的方式完成给定任务。**

因此，可用性既和界面有关，也和系统整体如何支持任务完成有关。
它不是视觉层的小修饰，而是产品是否真正可用的核心指标。

一个设计在视觉上可以非常精致，但仍然可能：
- 难学
- 易误解
- 易出错
- 干扰任务
- 让人疲惫
- 无法稳定复用

所以在本模块里，UI/UX 设计默认不以“审美完成度”作为第一判断标准，而以：
- 是否更容易理解对象
- 是否更容易找到下一步
- 是否更少误解和错误
- 是否更容易专注完成任务
- 是否更容易被学习、记忆和重复使用

作为主判断标准。

## 适用场景

- “帮我做这个产品的 UI/UX / UE 方案”
- “我不要只调视觉，先把信息架构和内容层级理清”
- “这个界面信息很多，但不知道先看哪块”
- “请重构主操作、状态区、待处理区、辅助区的布局”
- “这个后台 / 控制台 / workspace / studio / editor 像 demo，不像产品”
- “我需要复杂界面的交互设计，而不是换皮美化”
- “帮我从对象清晰、注意力聚焦、去歧义的角度重做界面”
- “请按重要程度、使用频率、当前最需要，重排界面信息”

## 先回答的 5 个问题

在讨论视觉前，必须先回答：

1. **当前界面的核心对象是什么？**
   - 用户现在到底在处理什么：文档、任务、画布、记录、会话、告警、素材？

2. **当前界面的核心决策是什么？**
   - 用户最常做的决定是什么：查看、编辑、确认、审阅、恢复、切换、提交？

3. **哪些信息必须先被看到？**
   - 风险、待处理、主对象身份、当前状态、下一步动作，谁优先？

4. **哪些信息不该常驻首屏？**
   - 低频说明、技术细节、机制解释、历史信息、二级元数据，是否应折叠？

5. **用户如何知道系统已经生效？**
   - 点击、切换、保存、应用、拒绝、恢复之后，有没有清晰反馈？

如果这 5 个问题答不清，就不要先讨论配色和留白。

## 核心设计原则

### 1. 对象清晰
首屏先说明：
- 我在看什么
- 我能操作什么
- 当前对象处于什么状态

不要让用户先读一堆机制说明，才能反推出当前对象是谁。

### 2. 注意力聚焦
人类和 Agent 的注意力都有限。
默认应该让界面先把注意力集中到：
- 当前主对象
- 当前主任务
- 当前异常 / 风险
- 当前待处理项

不要把所有信息都平铺成同权卡片。

### 3. 去歧义
同一类信息不要在多个区域同权重复表达。
必须尽量明确：
- 哪块是主真相区
- 哪块是主操作区
- 哪块是待处理区
- 哪块是辅助说明区
- 哪块是低频详情区

### 4. 排序先于美化
信息默认按以下维度排序：
1. **重要程度**：影响当前决策与安全感的优先
2. **使用频率**：高频操作优先
3. **当前最需要**：当前时刻最该处理的优先
4. **风险等级**：错误、冲突、丢失风险优先
5. **恢复成本**：出错后难恢复的优先

### 5. 条件出现优于永久常驻
以下内容优先考虑条件出现，而不是常驻：
- 异常说明
- 恢复指导
- 长段帮助文案
- 调试信息
- 次要统计

### 6. 视觉是增强器，不是遮羞布
如果信息结构混乱，单纯提升视觉精致度通常只会让错误层级“更好看地存在”。

## 可用性的心理学判断标准

从使用者心理负担与任务效率角度，可用性至少要满足：

1. **不分散注意力**
   - 设计不应不断把用户从手头任务拉走
   - 操作应尽量简单、稳定、可重复

2. **学习成本低**
   - 用户应能在较短时间内学会主要操作
   - 不应依赖大量培训、记忆或背景知识

3. **不要求过多系统知识**
   - 用户不需要理解底层硬件、软件、协议、实现细节，才能完成目标任务

4. **误解与错误最小化**
   - 用户不应频繁猜测按钮含义、状态含义、对象边界或动作后果
   - 重要动作应尽量去歧义，避免误操作

5. **支持专注完成任务**
   - 用户应能轻松把注意力集中在任务流本身，而不是界面解释或机制理解上

如果一个设计必须靠大量说明文案才能被正确使用，通常说明结构本身还不够自解释。

## 研究与测试原则

### 1. 可用性很少是偶然出现的
好的可用性通常不是“设计师刚好灵感很好”，而是：
- 先研究真实用户与真实任务
- 再提出结构与交互方案
- 再通过测试验证哪里仍然阻碍任务完成
- 再继续迭代

### 2. 研究先于方案，测试决定是否真的有效
如果没有研究，设计很容易在解决假问题。
如果没有测试，设计很容易停留在“看起来合理”，但并不知道是否真的有效。

### 3. 视觉正确不等于可用性正确
一个产品即使视觉上成熟、统一、精致，也仍然可能在：
- 信息排序
- 操作可发现性
- 状态理解
- 错误预防
- 恢复路径

这些真正决定体验的点上失败。

### 4. 可用性判断必须回到特定用户、特定场景、特定任务
不要抽象地问“这个页面好不好”。
要具体问：
- 谁在用
- 在什么场景下用
- 想完成什么任务
- 被什么阻碍
- 如何证明阻碍被消除了

## 框架层：界面设计、导航设计、信息设计

在本模块中，UI/UX 方案默认要同时区分并协同这三类设计：

1. **界面设计**：给用户“做某件事”的能力
   - 按钮、输入、选择、状态切换、确认、提交
2. **导航设计**：给用户“去某个地方”的能力
   - 全局导航、局部导航、辅助导航、上下文导航、远程导航
3. **信息设计**：给用户“理解内容与关系”的能力
   - 分组、排序、标签、指示标识、错误说明、帮助信息

这三者不能混成一句“把页面设计一下”。
很多所谓的“UI 问题”，实际可能分别属于：
- 界面控件不合适
- 导航关系不清楚
- 信息设计没有反映用户思路

## 习惯、一致性与谨慎打破常规

### 1. 优先利用用户已有习惯
如果某种交互模式已经是用户熟悉的默认预期，应优先复用，而不是为了新鲜感打破它。

### 2. 内部一致性比局部创意更重要
同一产品里，相同概念应尽量用相同表达：
- 相同对象命名
- 相同动作位置
- 相同状态反馈
- 相同确认方式

### 3. 可以违背习惯，但必须有充分理由
当你要违背常见模式时，至少应能回答：
- 带来的收益是什么
- 为什么值得增加学习成本
- 是否会破坏已有任务流

### 4. 少用需要猜测的比喻
如果一个图形、术语或视觉隐喻需要用户去猜它是什么意思，它通常就不是好的主表达方式。
直接表达通常比“有趣的比喻”更可靠。

## 推荐工作流

### Phase 1：对象与任务建模
先定义：
- Primary object
- Primary user
- Potential user（如有）
- Primary user action
- Primary risk
- Primary next step
- Review / confirmation boundary（如有）
- Usage context（环境 / 时间 / 情境限制）
- Current blockers（当前阻碍任务完成的因素）

### Phase 2：信息分层
把所有需要展示的信息分成 5 层：

1. **L1 主对象层**
   - 当前对象身份
   - 当前对象关键状态

2. **L2 主任务层**
   - 当前最该做的动作
   - 待处理项
   - 审阅/确认入口

3. **L3 异常与风险层**
   - error
   - conflict
   - stale
   - restore
   - blocking warning

4. **L4 辅助上下文层**
   - 次要统计
   - 补充状态
   - 协作说明
   - 历史摘要

5. **L5 低频详情层**
   - debug data
   - raw ids
   - technical metadata
   - advanced details

### Phase 3：区块职责设计
至少明确这些区块谁负责什么：
- Header
- Primary action area
- Navigation / sidebar
- Main content / canvas
- Pending / review area
- Status / feedback area
- Help / detail / debug area

### Phase 4：导航与指示标识设计
至少明确：
- 用户现在在哪
- 用户能去哪
- 这些选择之间是什么关系
- 当前页面与其他区域有什么关系
- 是否需要全局 / 局部 / 辅助 / 上下文导航
- 是否需要颜色、标签、图标、层级来强化“你在这里”的感觉

### Phase 5：状态与反馈设计
至少定义：
- 用户看见什么
- 哪些状态要常驻
- 哪些状态只在异常时出现
- 动作后如何反馈成功/失败/已定位/已保存/待确认

### Phase 6：视觉增强
在结构稳定之后，再补：
- 字号层级
- 对比与颜色语义
- 版式密度
- 间距系统
- 图标与装饰
- 动效与过渡

## 研究与诊断问题清单

在提出方案前，优先用这些问题校准：

- 谁是实际目标用户？是什么驱动他们使用这个产品？
- 谁是潜在用户？是什么阻止他们开始使用？
- 用户使用这个产品是为了完成什么任务？
- 用户所处的上下文是什么？有哪些环境、时间、设备、情境或长期约束？
- 当用户尝试完成任务时，当前到底被什么阻碍？
- 这些阻碍属于：信息不清、层级错误、布局不合理、反馈不足、术语歧义，还是系统能力本身不足？
- 哪些障碍可以通过信息结构、内容布局、视觉权重、状态反馈来消除？
- 哪些问题必须通过真实测试才能验证，而不能只靠主观判断？

如果这些问题没有被问清，方案通常会过早落入“美化界面”，而不是“解决使用问题”。

---

## 线框图与页面框架

线框图不只是低保真草图，而是框架层的集成文档。
它至少应承载：
- 核心区块
- 核心操作
- 导航关系
- 信息优先级
- 关键状态
- 需要补充说明的特殊行为

文档本身不是目的，但如果没有任何方式把这些关系显式表达出来，后续视觉设计与实现都容易偏离原意。

## 表现层：视觉如何支持结构

### 1. 先问“是否运作良好”，再问“是否美观”
视觉设计首先要回答：
- 是否强化了结构
- 是否强化了主对象与主任务
- 是否帮助用户看清可选项与状态差异
- 是否表达了正确的品牌与产品定位

### 2. 第一眼注意力落点必须正确
可直接用这些问题快速评估：
- 用户第一眼先看到什么？
- 这是不是当前最重要的对象/动作/风险？
- 视线移动是流畅的，还是在页面上乱跳？

### 3. 对比用于建立重点，不是制造热闹
对比太少，页面会灰；
对比太多，页面会吵。
目标不是刺激，而是让重要内容更易被感知。

### 4. 一致性用于降低认知负担
一致的尺寸、样式、状态表达、标签系统，会减少用户猜测和焦虑。

## 常见失败模式

### F1. 把所有该展示的信息都平铺展示
问题：信息存在，但没有优先级，导致没人知道先看哪块。

### F2. 用视觉精致感掩盖结构混乱
问题：更美，但更难用。

### F3. 机制说明先于任务对象
问题：用户先看到系统怎么实现，而不是当前工作对象与下一步。

### F4. 同类状态多处重复
问题：状态不少，但真相源缺失。

### F5. 高风险动作没有清晰确认边界
问题：用户不知道什么时候只是提议，什么时候已生效。

### F6. 低频内容长期占据首屏
问题：帮助、说明、元数据与主任务争抢注意力。
