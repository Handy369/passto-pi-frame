# User Experience Elements — 五层法提炼

> **last_verified: 2026-05-16**
> source note: 提炼自《用户体验要素：以用户为中心的产品设计》相关核心方法，并按本地 skill 体系重组

## 作用

本文件不是替代现有 references，而是作为一个**跨层总纲**，帮助本地 product-definition 技能在“战略 → 范围 → 结构 → 框架 → 表现”之间保持一致。

它主要解决两个常见问题：
1. 只会直接讨论页面或功能，却说不清为什么做、做到哪一步为止
2. 把“结构层”误当成“技术架构层”，或把“视觉层”误当成“审美层”

---

## 五层总览

| 层级 | 核心问题 | 本地 skill 映射 | 关键提醒 |
|---|---|---|---|
| 战略层 | 为什么做？为谁做？怎么判断成功？ | `discovery.md` / `research.md` / `spec-and-scope.md` | 先定目标与用户需求，不先列功能 |
| 范围层 | 这次到底做什么、不做什么？ | `spec-and-scope.md` / `feature-map-and-prioritization.md` | scope 同时包含功能与内容 |
| 结构层 | 这些能力如何组成可理解的整体？ | `core-flow-design.md` | 这里更接近交互结构 / 信息架构，不等于技术架构 |
| 框架层 | 用什么界面、导航、信息排布来承载结构？ | `ui-ux-product-design.md` | 界面、导航、信息设计要分开看，又要一起落地 |
| 表现层 | 最终感知上如何强化结构与目标？ | `ui-ux-product-design.md` / `design-foundation.md` | 视觉要支持结构、任务与品牌，不是独立表演 |

## 1. 战略层：产品目标和用户需求

### 重点不是“想做什么功能”，而是：
- 我们想达成什么产品/商业结果
- 哪些用户需求值得优先满足
- 成功如何被定义和验证

### 最小战略输入
- Product goals
- User needs
- User segments
- Success criteria
- Brand / positioning constraints

### 关键原则
1. **目标要短，但必须能指导取舍**
2. **成功标准要可验证，而不是“做出来看看”**
3. **人物角色 / personas 不是装饰物，而是帮助团队持续记住用户**
4. **战略文档不是归档品，而是项目期间反复使用的判断依据**

### 对本地 skill 的影响
- `discovery.md`：更适合澄清问题、机会、假设
- `research.md`：更适合沉淀用户证据、分层、行为模式
- `spec-and-scope.md`：更适合把战略转成这次版本的明确范围

## 2. 范围层：功能规格和内容需求

### 范围层回答的是
> **这次到底要做什么，以及明确不做什么。**

它不是 feature wishlist，而是战略在本版本的可执行投影。

### 关键原则
1. **定义范围的价值，一半在“知道做什么”，另一半在“知道不做什么”**
2. **scope 不只包含功能，也包含内容**
   - 帮助文案
   - 错误提示
   - 空状态
   - 引导内容
   - 审核/发布/维护内容
3. **需求必须可理解、可验证、少歧义**
4. **优先级应同时看战略匹配、用户价值、可行性**
5. **未纳入本次范围的好想法，应沉淀为后续版本候选，而不是临时插队**

### 需求写法四原则
- **正向描述**：写系统应如何帮助用户，而不是只写“不允许什么”
- **具体**：不要写“重点展示”“智能推荐”这类空话，要写清条件与行为
- **避免主观词**：少用“高级”“时尚”“流畅”等不可验证表达
- **可验证**：必须能判断“是否满足”

### 内容需求补充
内容也是工作，不是上线前最后补文案：
- 内容类型
- 内容规模
- 内容 owner
- 更新频率
- 内容清单 / inventory

## 3. 结构层：交互设计与信息架构

### 本地语境下要特别区分
书里的“结构层”主要指：
- 交互设计
- 信息架构
- 概念模型
- 模式与顺序

它**不等于**系统容器图、服务拆分、数据建模那类技术架构。

### 结构层回答的是
- 用户动作与系统响应如何组成一套可预测的流程
- 信息与功能如何被组织成一个能理解、能成长的整体

### 关键原则
1. **先定义模式与顺序，再谈页面外观**
2. **概念模型要统一**
   - 同一个对象不要一会儿当“容器”，一会儿当“地点”
3. **错误处理不只是报错提示**
   - 预防错误
   - 让错误更难发生
   - 发生后帮助识别与恢复
4. **步骤合理性比“点击更少”更重要**
5. **信息架构既要反映当前需求，也要能容纳未来增长**
6. **组织原则必须贴近用户目标与用户语言**
7. **受控词典与元数据会决定结构能否长期稳定演化**

### 常见结构方法
- Hierarchical
- Matrix
- Organic
- Sequential

没有哪一种天然最好，取决于：
- 用户目标
- 内容性质
- 是否要求探索
- 是否要求严格顺序

## 4. 框架层：界面设计、导航设计、信息设计

### 这一层要把三件事分清
1. **界面设计**：给用户做事的能力
2. **导航设计**：给用户去别处的能力
3. **信息设计**：把信息组织成易理解、易使用的表达

### 关键原则
1. **好界面不是把所有可能都平等展示出来**
2. **应该优先支持高频主任务，而不是为了边缘情况牺牲大多数人**
3. **要尽量利用已有习惯与一致性，谨慎打破用户预期**
4. **不要滥用比喻，能直接表达就不要让用户猜**
5. **导航要同时回答：我能去哪、这些选项之间什么关系、它们和当前页面什么关系**
6. **信息设计要反映用户思路，而不是反映内部组织结构**
7. **线框图是框架层的集成文档，不只是占位草图**

### 线框图最该承载的内容
- 核心区块
- 核心操作
- 导航体系
- 信息优先级
- 状态与反馈
- 关键注释 / 特殊行为

---

## 5. 表现层：感知设计 / 视觉支持

### 表现层回答的是
> 在已经明确的框架基础上，最终如何被用户感知到。

### 关键原则
1. **视觉设计应支持战略、范围、结构、框架，而不是反过来破坏它们**
2. **先问“是否运作良好”，再问“是否好看”**
3. **第一眼注意力落点必须服务任务与目标**
4. **对比用于建立注意力与群组，不是为了制造热闹**
5. **一致性用于降低认知负担，减少焦虑与猜测**
6. **品牌表达也应服从定位与任务，不只是审美偏好**

### 实用评估法
- 第一眼先看见什么？
- 第一眼被看见的是否就是最重要的对象/动作/状态？
- 视线移动是否流畅？
- 页面是有引导，还是所有元素都在抢注意力？
- 视觉处理是否强化了结构，而不是掩盖结构问题？

## 推荐的本地落地顺序

1. `discovery.md`
   - 先澄清机会、用户、情境、风险假设
2. `research.md`
   - 用证据支持用户需求、分层、行为模式
3. `spec-and-scope.md`
   - 把战略压成目标、边界、成功标准、范围
4. `feature-map-and-prioritization.md`
   - 把 scope 拆成功能/内容结构与优先级
5. `core-flow-design.md`
   - 把功能与内容组织成模式、顺序、异常恢复
6. `ui-ux-product-design.md`
   - 落到界面、导航、信息设计与视觉增强

## 常见误区

### 误区 1：直接从页面开始画
结果：页面很多，但目标、范围、结构全都不稳定。

### 误区 2：把“结构层”误当成“系统架构图”
结果：技术方案很多，但用户如何理解和穿行产品并不清楚。

### 误区 3：把视觉设计当成独立审美工作
结果：界面更精致，但任务更难完成。

### 误区 4：只列功能，不列内容
结果：错误提示、帮助信息、空状态、说明文案最后都临时补，体验变差。

### 误区 5：优先级只看想法大小，不看战略匹配
结果：scope creep，版本失控。
